# Банк инженерных идей

Этот банк сохраняет знания из исследования и объясняет выбор рабочих правил. Он не загружается автоматически и не добавляет обязательных действий к каждой задаче. В AGENTS.md остаётся короткое ядро; подробность читается по соответствующей задаче.

## Основной синтез

| Идея | Практическое применение | Где принято |
| --- | --- | --- |
| Форма задачи должна вести к исходной пользе | Назвать понимание существенного запроса, ожидаемый эффект и ближайший проверяемый результат; продолжать понятную работу | AGENTS.md |
| Архитектура сокращает область необходимого понимания | Читать затронутый контракт и расширять контекст по обнаруженным зависимостям | AGENTS.md, architecture.md |
| Низкое зацепление, высокая внутренняя связность | Скрывать чужие детали; собирать данные и правила одной ответственности вместе | architecture.md |
| Заменяемость — поведенческая гарантия | Проверять обещания потребителю, ошибки и существенные ограничения после смены реализации | architecture.md |
| У данных и решения есть владелец | Другие модули вызывают ясные операции; точки записи, права и момент фиксации определены | architecture.md, runtime.md |
| Абстракция должна уменьшать сложность | Выбирать слой, сервис или событие ради реального свойства; оценивать цену эксплуатации и изменения | architecture.md |
| Данные проверяют предметную модель | До закрепления нового контракта сверять значимые предпосылки с реальными примерами | architecture.md |
| Минимальная FSM сохраняет существенные различия | Различать ожидающий, неизвестный, отменяемый и завершённый исходы, если от них зависит поведение | runtime.md |
| Внешний эффект требует понятного восстановления | Идемпотентность, ограниченный повтор, отмена, конкурирующая запись и сверка неизвестного результата | runtime.md |
| Интеграцию определяет фактический протокол | Документация нужной версии, исходники при пробеле и изолированный пример по неизвестности; для WS — восстановление потока | runtime.md |
| Логи отвечают на вопросы о причине | Стабильные события, необходимые идентификаторы, переходы, причина и результат; наблюдаемость по сложности сценария | runtime.md |
| Проверка должна различать правильное и правдоподобно ошибочное поведение | Независимые ожидания, значимые края, регрессии и нужный уровень интеграции | verification.md |
| Property-based тесты усиливают устойчивые свойства | Проверять инварианты и последовательности; сами свойства выводить из правил продукта, включая исключения | verification.md |
| Вертикальная часть ускоряет обратную связь | Рано провести полезный сценарий через границы и проверить предпосылку, которая меняет решение | verification.md |
| Готовность имеет несколько наблюдаемых этапов | Показывать, что реализовано, проверено и доступно в нужной среде по поручению; при оставшейся цели предлагать следующий шаг | verification.md |
| Знание должно переживать смену исполнителя | Действующие команды, примеры, контракт и существенное «почему» хранить рядом с проектом | AGENTS.md, verification.md |
| Средства разработки должны убирать реальное ожидание | Устойчивые проверки закреплять в инструментах; стек выбирать по нужной гарантии и стоимости | environment.md |
| Процесс полезен при конкретной причине | Глубину плана, исследования, проверки и координации выбирать по неопределённости и последствиям | Весь набор |

Формулировки выше — наш синтез. FSM, WS, идемпотентность и схема причинных логов конкретизируют запрос пользователя; они не приписываются Борщёву как дословные рекомендации.

## Что оставлено справочным

- Схемы организации команд, найм, увольнение, личный распорядок, обучение и публикации — контекст для человека. Они помогают понять происхождение идей об автономии и понятной передаче работы, но не задают агенту календарь или кадровые действия.
- Конкретные версии Django, инструменты CI, SaaS и примеры Docker — исторические реализации. Переносится проверяемая гарантия, а актуальную команду определяет проект.
- Числа из частных практик — размер PR, процент покрытия, длительность спринта, число участников — примеры выбора. Рабочее правило связывает объём с риском и стоимостью понимания.
- Частота выпуска и ручные этапы приёмки определяются поручением и процессом проекта. Из источников взяты ранняя обратная связь, обозримость результата и путь восстановления.
- Позиции автора об AI менялись. В [посте 1349](https://t.me/pmdaily/1349) пересмотрен ранний запрет [1306](https://t.me/pmdaily/1306) на тесты с LLM. В наборе закреплены независимая спецификация поведения и подходящая проверка, без нового универсального ожидания человека.
- [Совет о пустом глобальном CLAUDE.md](https://t.me/pmdaily/1367) усиливает воспроизводимость проектного знания. В Codex личные глобальные настройки сохраняются на предусмотренном официальной документацией уровне.

Проверяем качество набора по последующим реальным задачам: меньше ли ненужного чтения и ожидания, верно ли выбирается глубина проверки, локализуются ли изменения и доводится ли работа до порученного результата. Текущая редакторская и статическая проверка подтверждает структуру файлов и согласованность формулировок.
